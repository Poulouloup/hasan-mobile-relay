# Hasan Bridge Diagnosis

Use this skill when a user reports the Hasan Android app can't connect
(chat, phone bridge/pairing, or the relay itself), or asks how the Hasan
server-side deployment is wired together.

## 1. Architecture overview

The app only speaks `https://`/`wss://` to a **hostname** whose certificate
is trusted by Android (standard TLS verification — no self-signed
certificate, no bare IP address, no trust prompt). Two hostnames front the
two services, because each serves its own paths from the root:

| Hostname (example) | Service | Listens on | Runs as |
|---|---|---|---|
| `hasan.example.net` | relay server (Android WebSocket bridge, `/ws`) | `8767` | Docker container `hasan-relay`, published on host `127.0.0.1:8767` only |
| `hermes.example.net` | hermes-webui (chat backend) | `8787` | native Hermes: systemd **user** service `hermes-webui`; containerised Hermes: inside the Hermes container |

Port 443 is held by a reverse proxy (Caddy). `server/install.sh` picks one
of three layouts, and the upstream addresses differ in each:

| Layout | When | Relay upstream | webui upstream |
|---|---|---|---|
| own Caddy | port 443 was free: the installer launched `hasan-bridge-caddy` (`network_mode: host`) | `127.0.0.1:8767` | `127.0.0.1:8787` |
| existing proxy, host network | 443 held by a native process or a host-network container | `127.0.0.1:8767` | `127.0.0.1:8787` |
| existing Caddy on a Docker network | 443 held by a container on a regular Docker network | `hasan-relay:8767` (the relay is attached to that network) | `<gateway of that network>:8787` (webui listens on that gateway) |

The third layout exists because a container on a regular Docker network
**cannot reach the host's `127.0.0.1`** — that address is its own. Typical
symptom of getting it wrong: `502 Bad Gateway` from Caddy on both hostnames
while both services answer fine locally.

The `hasan_delivery` plugin runs inside the Hermes gateway process and
reaches the relay locally (`HASAN_RELAY_URL=http://127.0.0.1:8767`), with
the relay's admin token (`HASAN_RELAY_ADMIN_TOKEN`) — never through the
public hostname, never with a phone's session token.

Config file locations:
- `server/.env` (secrets: `RELAY_ADMIN_TOKEN`, `WEBUI_URL`/`WEBUI_PASSWORD`) — never `cat` this directly, it holds a live secret.
- `server/docker-compose.yml` — the compose manifest, versioned in git, safe to read. `server/docker-compose.network.yml`, when present, was generated by `install.sh` and attaches the relay to an existing Caddy's Docker network.
- `server/Caddyfile` — exists only in the "own Caddy" layout (rendered from `server/Caddyfile.template`; first line has a `# managed-by: hasan-bridge docker compose` marker). In the other two layouts the routing lives in the **existing** proxy's own config, which this deployment does not own.
- `~/.config/hasan/webui.env` (secret: webui password, listen address) and `~/.local/share/hasan/webui-start.sh` — native Hermes only, written by `install.sh`.
- `${HERMES_HOME}/.env` — `HASAN_RELAY_URL`, `HASAN_RELAY_ADMIN_TOKEN` for the plugin (holds the user's API keys too — never `cat`).
- `${HERMES_HOME}/plugins/hasan_delivery/` — plugin code.

## 2. The two-reverse-proxies trap

On 2026-07-28, hours were lost to two Caddy configs disagreeing about
where to route `:443` — one loaded by a manually-started `nohup caddy run`
process, another by the systemd `caddy.service` package unit, each
pointing at a different backend port. The symptom was misleading: repeated
`401 Unauthorized` on login that looked like a credentials problem but was
actually requests landing on the wrong backend entirely.

`install.sh` therefore never starts a second proxy: if anything else holds
port 443 it reuses it and prints the two site blocks to add. But a process
started *after* the installation could still collide. If something looks
wrong, always check for a second listener first, before assuming a config
or credentials problem.

A separate, pre-existing skill (`hermes-web-ui-remote-access`) documents
port 9119 as the Hermes dashboard's backend. That is a different service
from hermes-webui (8787); this deployment does not expose the dashboard.

## 3. Common diagnostic commands (read-only)

```bash
# Relay container state and logs
docker compose -p hasan-bridge ps
docker compose -p hasan-bridge logs --tail 100 relay

# Health, from the inside out — the first failing line locates the problem
curl -sf http://127.0.0.1:8767/health                 # relay itself
curl -sf http://127.0.0.1:8767/version                # 0.2.0+ required by the current plugin
curl -sf http://<webui listen address>:8787/health    # webui itself (127.0.0.1, or the Docker network gateway)
curl -sf https://hasan.example.net/health             # relay through the reverse proxy
curl -sf https://hermes.example.net/health            # webui through the reverse proxy
# No -k anywhere: if curl needs -k, the app will refuse the certificate too.

# Which listener actually owns port 443, and how it is networked
ss -ltnp 'sport = :443'
docker ps --format '{{.Names}}\t{{.Ports}}' | grep ':443->'
docker inspect <proxy container> --format '{{.HostConfig.NetworkMode}}'
docker inspect hasan-relay --format '{{range $n, $_ := .NetworkSettings.Networks}}{{$n}} {{end}}'

# webui (native Hermes)
systemctl --user status hermes-webui
journalctl --user -u hermes-webui -n 100
grep -c . ~/.config/hasan/webui.env        # exists and non-empty, without printing the password

# Plugin
journalctl --user -u hermes-gateway.service -n 200 | grep -i hasan_delivery
hermes plugins list | grep -i hasan
```

Reading the app's own error (Settings → Connections) narrows it down
before any command:

- "Certificat du serveur non reconnu" → the proxy serves a self-signed or
  expired certificate for that hostname (`tls internal`, failed ACME
  issuance).
- "ne correspond pas à son nom d'hôte" → the app was given an IP address or
  a hostname the certificate does not cover.
- "Serveur injoignable … Tailscale" → DNS or network: the server is only
  reachable from the home network or through Tailscale.

## 4. fail2ban awareness

A `hermes-webui` jail watches the Caddy access log for repeated failed
logins (`maxretry=5`, `bantime=3600`). Running repeated diagnostic curl
calls against `/api/auth/login` from the same source IP during
troubleshooting can self-inflict a ban. If a previously-working IP
suddenly gets connection-refused/reset, check:

```bash
fail2ban-client status hermes-webui
```

before assuming a routing or credentials problem.

## 5. FCM wake-up for proactive notifications (app closed / no active WS)

The relay can wake the Android app via Firebase Cloud Messaging (data-only,
never carries message text) when a proactive push (`POST /phone/message`
with no active WebSocket for that device) needs to reach a fully-closed
app. This is a separate accelerator on top of the existing WS + push-buffer
delivery path — not a replacement for it.

Flow: `POST /phone/message` (no WS) → `push_buffer.push()` (unchanged) →
`server.py::_send_fcm_wake()` sends `{"type":"wake"}` via `firebase-admin`
→ device's `HasanFirebaseMessagingService.onMessageReceived()` fires →
`GET /phone/pending` (session-token auth — this call comes from the phone) drains the buffer → real Android
notification via `ProactiveNotifier.show()`.

Config/state involved:
- `RELAY_FCM_CREDENTIALS_PATH` env var on the relay (see `DEPLOYMENT.md`) — path to the Firebase service-account JSON. Absent
  or invalid → `_init_fcm_app()` logs a warning and returns `None`;
  `/phone/message` keeps working exactly as before (WS + buffer only), no
  crash, no exception surfaced to the caller.
- `Session.fcm_token` (`server/relay/pairing.py`) — the device's current
  FCM token, synced via `POST /fcm-token` (session-token auth). Synced from
  three points app-side: `onNewToken()`, right after a successful pairing,
  and as a best-effort refresh on every WS `onOpen()` — so a token learned
  while offline still reaches the relay on the next reconnect even without
  a fresh `onNewToken()` firing.
- `GET /phone/pending` is NOT the same as `GET /phone/outbound` — pending
  drains (removes) buffered envelopes, outbound is a read-only peek. Don't
  conflate the two when debugging a "message never arrived after wake"
  report — draining twice in a row correctly returns an empty list the
  second time, that's not a bug.

**Known false-negative when testing manually**: `adb shell am force-stop
<pkg>` puts the app in a persistent "stopped" state that Android
deliberately blocks ALL external wake-ups for (FCM included) until the app
is relaunched by the user — confirmed via `W/GCM: broadcast intent
callback: result=CANCELLED` in logcat. This is not a bug in this delivery
path; it reproduces the same restriction as the user tapping "Force stop"
in system Settings. To test a real closed-app scenario, use the app's own
"Quitter" button (drawer → confirm) or a full device reboot instead —
both were verified end-to-end on a real device (Pixel 10, Android 16) and
deliver correctly; only the `am force-stop` shortcut is unreliable as a
test method.

```bash
# Watch for the two log lines that confirm the FCM path was taken
docker compose -p hasan-bridge logs -f relay | grep -i fcm
# "Réveil FCM envoyé device_hash=..." = firebase-admin accepted the send
# "Échec envoi FCM device_hash=..." = send failed (stale token, bad creds) — logged only, never raised
```

## Non-goals

This skill is diagnostic only. It never restarts or recreates containers
(`docker compose down`/`restart`/`up --force-recreate`, `docker rm`),
never edits `server/Caddyfile`/`server/.env` or the existing reverse
proxy's config by hand, and never regenerates pairing or session tokens. For a fix, re-run
`server/install.sh` (idempotent, safe to re-run) or hand off to a
human operator.
